# Exploration: data-model-core — Supabase data model & RLS baseline

The persistence layer every later feature builds on. This change lands the full core
schema (customers, orders, products, inventory, transactions, profiles), the RLS
security boundary, the `is_admin()` role seam, and generated TypeScript types — but
**no** data-access layer and **no** auth UI. Decision summary first; detail below.

## Decision Summary

| # | Question | Decision | One-line rationale |
|---|----------|----------|--------------------|
| 1 | Migration & type tooling | **Supabase CLI** (SQL migrations + `supabase gen types`) | Native path for Postgres + RLS + realtime + security-definer; zero ORM impedance. Drizzle/Prisma are ORMs that can't express RLS or security-definer functions and would fork schema truth |
| 2 | Schema primitives | Postgres **enums** for stable statuses; **text + CHECK** for open lists (payment method, product type); **UUID** PKs; `timestamptz` timestamps; `date` for `due_date`; `jsonb` for per-part colors; **hard delete** | Enums are typed and self-documenting; UUIDs match `auth.users` and avoid enumeration on the future public catalog; CHECKs stay cheap to extend |
| 3 | RLS + roles | `anon` no workshop access; `authenticated` staff read/write; **admin-only** for `transactions`; `security definer` `current_user_role()`/`is_admin()` in a `private` schema | Role enforcement lives in ONE function so roles-hardening later changes nothing but that function |
| 4 | First-slice boundary | **Full core schema in ONE change** (~550–720 reviewable lines) | Tables are FK-coupled (transactions→orders→customers); splitting breaks referential integrity. Fits 800-line budget with no data-access layer |
| 5 | Local dev / verify path | **Supabase local** (CLI + Docker) primary; cloud project deferred | Migrations + types + RLS tests run hermetically, no prod credentials. Docker Desktop is a missing prerequisite today |
| 6 | Change scope | **Schema + RLS + types + enum constants only** | Typed query helpers are speculative without a consumer; orders-core defines them from real usage |

## Approaches

### Q1 — Migration & type-generation tooling

| Dimension | Supabase CLI (SQL) | Drizzle | Prisma |
|-----------|-------------------|---------|--------|
| RLS policies | Native, first-class (`CREATE POLICY`) | Not expressible in schema DSL — hand-written SQL outside the ORM | Not expressible — needs shadow SQL |
| Security-definer functions | Native | Hand-written SQL, unmanaged | Hand-written SQL, unmanaged |
| Realtime publications | `supabase/config.toml` + SQL | Not covered | Not covered |
| TS types | `supabase gen types` (from live schema) | `drizzle-kit` (from schema) | `prisma generate` (from schema) |
| Single source of truth | One SQL migration dir | Schema DSL **plus** migrations diverge | Schema DSL **plus** migrations diverge |
| App fit | Matches existing direct `supabase-js` usage (foundation decision #3) | Adds an ORM layer the app never asked for | Adds an ORM layer the app never asked for |

**Recommendation: Supabase CLI.** The app already queries through `supabase-js`
directly; RLS + security-definer functions + realtime are the actual features of this
stack, and only raw SQL migrations express them without a parallel truth. Drizzle and
Prisma solve "portable schema + typed client" for apps that own their DB; here the DB
features (RLS) are the product and the generated types already come free from
`supabase gen types`. Cost: no ORM ergonomics — acceptable for a small team writing
~6 tables of hand SQL.

### Q2 — Schema primitives (enums vs lookup vs CHECK, PKs, timestamps, deletes)

- **Enums (Postgres `CREATE TYPE`)** for `order_status` and `transaction_type`:
  low-churn, closed value sets that map cleanly into generated union types and are
  self-documenting. Changing an enum value requires `ALTER TYPE` in a later migration —
  acceptable for statuses.
- **`text` + `CHECK` constraint** for `payment_method` (cash, transfer, ualá, brubank,
  mercadopago, other…) and `product_type` (cup, trophy, keychain, other…): the
  requirements explicitly say "etc." for payment methods and product types will evolve;
  CHECK lists extend with a trivial migration and no `ALTER TYPE ... DROP VALUE` pain.
- **`jsonb`** for `orders.color_spec` — per-part color is open-ended
  (`{ "part_a": "black", "part_b": "blue" }`); a fixed `part_a_color`/`part_b_color`
  pair would not scale to N parts.
- **UUID PKs** (`gen_random_uuid()` default): matches `auth.users.id` (profiles FK),
  avoids ID enumeration when `products` becomes public, safe in URLs. Bigint would be
  marginally simpler but clashes with Supabase Auth and leaks row counts.
- **`timestamptz`** for `created_at`/`updated_at`/`order_date`/`transacted_at`;
  **`date`** for `orders.due_date` (a delivery *day*, used for agenda sorting and the
  Urgent/Today traffic-light — no time component). Standard `set_updated_at()` trigger
  keeps `updated_at` honest.
- **Hard delete** for operational rows; `ON DELETE RESTRICT` on
  `transactions.order_id` and `ON DELETE CASCADE` on `orders.customer_id`/variants.
  Soft delete is deferred to `catalog-phase1` where `products` get an `active` flag
  because historical orders reference them.

### Q3 — RLS + role strategy

- `anon`: **no** access to any workshop table in this change (catalog read comes later).
- `authenticated` (workshop staff): read/write customers, orders, products, inventory;
  read profiles.
- **`transactions` = admin-only** read AND write: it is the income registry for daily
  reconciliation — the single most financially sensitive table, and it has no operator
  need in the first slices.
- `private.current_user_role()` and `public.is_admin()` as `security definer` functions
  with `set search_path = ''`, reading `public.profiles(role)`. All policies that need a
  role route through them, so `roles-hardening` changes ONE function body, never
  policies, never the frontend.
- `profiles` is auto-created by an `on_auth_user_created()` trigger (id FK →
  `auth.users`, `role` default `'operator'`).

**Deferred financial nuance (explicit):** Postgres RLS is row-level, not column-level.
Order financial columns (`total_amount`, `deposit`, `pending_balance`) remain readable
by operators in this change. Column-level restriction requires a `orders` view + column
grants, which is the designated work of `roles-hardening` (the requirements say
"restrict financial visibility later"). `transactions` being admin-only already covers
the reconciliation register.

### Q4 — First-slice boundary

**Recommendation: full core schema in one change.** `transactions.order_id` and
`orders.customer_id` are FK-coupled; splitting transactions/inventory out would ship a
broken FK graph (or a deferred FK) and force a second migration to repair it. Size
forecast (reviewable lines, generated types + lockfile excluded per session config):

| Component | ~Lines |
|-----------|--------|
| 6 tables + enums + constraints + indexes | 300–400 |
| `set_updated_at` + `on_auth_user_created` triggers, `is_admin`/`current_user_role` | 60–100 |
| RLS policies (~6 tables) + grants | 120–180 |
| `supabase/config.toml` + seed.sql | 40–60 |
| **Total** | **~520–740** |

Fits the 800-line budget. Fallback if design reveals overrun: split `inventory`
(leaf table, no inbound FK) into a follow-up — but do **not** split transactions.

### Q5 — Local dev / verification path

**Recommendation: Supabase local (CLI + Docker) primary.** `supabase init` →
`supabase start` → `supabase migration new` → `supabase db reset` gives a hermetic
Postgres with RLS and realtime, so apply/verify can: apply migrations, run
`supabase gen types --local`, and exercise RLS policies (as anonymous vs authenticated)
with zero production credentials. The existing smoke test can be pointed at the local
project.

**Flagged:** Docker Desktop and the Supabase CLI are **not installed** on this machine
(`docker` not found; `supabase` CLI not found, `npx supabase` = 2.115.0 works). Both are
prerequisites for the apply/verify path and must be provisioned before apply. A real
Supabase cloud project is **eventually required** (deploy, edge functions, production
smoke) but is **not** blocking this change — generated types come from `--local`.

### Q6 — Change scope

**Recommendation: schema + RLS + types + a small enum-constants module, nothing more.**
The generated types are the durable value. Typed query/repository helpers are
speculative until `orders-core` defines real query shapes, and every speculative helper
would be rewritten against real usage — dead weight now. Ship:

1. SQL migrations (schema, enums, triggers, RLS, grants).
2. `src/lib/database.types.ts` (generated) wired into `supabase.ts`.
3. `src/lib/domain-constants.ts` — tiny module mapping `order_status` values →
   labels/colors for the kanban/agenda (genuinely reusable, ~20 lines).

Defer the typed data-access layer to `orders-core`, which consumes it first.

## Recommendation

Land the **full core schema + RLS baseline + generated types in one change** using the
**Supabase CLI**, with **UUID PKs**, **enums for closed sets / CHECK for open lists**,
**admin-only `transactions`**, and the `is_admin()` security-definer seam. Verify via
**Supabase local (Docker)**; no data-access layer yet.

## Risks

- **Docker Desktop + Supabase CLI not installed** — blocks the local verify path; must
  be provisioned before `apply`.
- **RLS misconfiguration exposes financial data** — `transactions` admin-only now, but
  order amounts remain operator-readable until `roles-hardening`; the design MUST
  include a negative RLS test checklist (anon/operator vs admin access assertions).
- **Smoke test stays skipped** until a real project is provisioned — acceptable
  (local RLS tests compensate), but connectivity smoke remains unproven in CI.
- **Enum vs CHECK friction** — if `payment_method` or `product_type` need re-listing,
  a CHECK migration is cheap but must not be forgotten in future changes.
- **Type/schema drift** — every migration requires a `supabase gen types` re-run; the
  verify phase must assert `database.types.ts` is up to date (add a script/gate).
- **Security-definer recursion** — role functions must use `security definer` +
  `set search_path = ''` to avoid RLS recursion and search-path injection (Supabase
  best-practice pattern).
- **`product_type` as free text** — intentionally not FK-constrained to `products`
  (orders predate the catalog); revisit in `catalog-phase1`.

## Ready for Proposal

**Yes.** All six questions have committed recommendations and a sized slice boundary
(~520–740 reviewable lines vs 800 budget). The orchestrator should move to `sdd-propose`
and flag to the user that Docker Desktop + Supabase CLI must be installed before
`apply`.
