# database-schema

Core persistence schema: six workshop tables plus `profiles`, with enums, CHECK constraints, UUID primary keys, foreign keys, indexes, and create/update triggers.

## Requirements

### Requirement: Core Tables

The system MUST provide the tables `profiles`, `customers`, `orders`, `products`, `product_variants`, `inventory`, and `transactions` in the Supabase Postgres database. Every table MUST use a UUID primary key generated by `gen_random_uuid()`.

#### Scenario: All core tables exist

- GIVEN a fresh database with migrations applied
- WHEN the schema is inspected
- THEN the seven tables exist
- AND each has a UUID primary key

### Requirement: Enums for Closed Value Sets

The system MUST define Postgres enum `order_status` with values `new`, `in_queue`, `printing`, `post_processing`, `finished`, `cancelled`, and `transaction_type` with values `3d_service`, `supplies_sale`. Columns using these sets MUST be typed to the enum, not free text.

#### Scenario: Order status accepts enum values only

- GIVEN the migrations are applied
- WHEN an `orders` row is inserted with `status = 'printing'`
- THEN the insert succeeds
- AND a value outside the enum (e.g. `shipped`) is rejected

#### Scenario: Transaction type uses the enum

- GIVEN the migrations are applied
- WHEN a `transactions` row is inserted with `type = '3d_service'`
- THEN the insert succeeds
- AND a value outside the enum is rejected

### Requirement: CHECK Constraints for Open Lists

The system MUST constrain `payment_method` and `product_type` as `text` columns with CHECK constraints. `payment_method` MUST allow at least `cash`, `transfer`, `uala`, `brubank`, `mercadopago`, `other`; `product_type` MUST allow at least `cup`, `trophy`, `keychain`, `other`. New values SHALL be extensible via a migration without altering an enum type.

#### Scenario: Known value is accepted

- GIVEN the migrations are applied
- WHEN an `orders` row is inserted with `payment_method = 'mercadopago'`
- THEN the insert succeeds

#### Scenario: Unknown value is rejected

- GIVEN the migrations are applied
- WHEN an `orders` row is inserted with a value outside the CHECK list
- THEN the insert is rejected by the CHECK constraint

### Requirement: Column Types

The system MUST use `timestamptz` for `created_at`, `updated_at`, `order_date`, and `transacted_at`; `date` for `orders.due_date`; and `jsonb` for `orders.color_spec` (per-part color map such as `{ "part_a": "black" }`). Monetary columns MUST be `numeric`.

#### Scenario: Color spec stores a per-part map

- GIVEN the migrations are applied
- WHEN an `orders` row stores a JSON object in `color_spec`
- THEN the object round-trips as JSON, not a flattened string

#### Scenario: Due date has no time component

- GIVEN the migrations are applied
- WHEN an `orders` row is inserted with a `due_date`
- THEN the stored value is a calendar date with no time-of-day

### Requirement: Amount Validation

The system MUST enforce, via CHECK constraints, that `orders.total_amount`, `orders.deposit`, and `orders.pending_balance` are non-negative, and that `orders.deposit <= orders.total_amount`.

#### Scenario: Over-deposit is rejected

- GIVEN the migrations are applied
- WHEN an `orders` row is inserted with `deposit > total_amount`
- THEN the insert is rejected

### Requirement: Foreign Key Integrity

The system MUST enforce referential integrity: `profiles.id` FK to `auth.users`; `orders.customer_id` FK to `customers` with `ON DELETE CASCADE`; `product_variants.product_id` FK to `products` with `ON DELETE CASCADE`; `transactions.order_id` FK to `orders` with `ON DELETE RESTRICT` and nullable (for supplies sales).

#### Scenario: Deleting a customer cascades to orders

- GIVEN a customer with orders exists
- WHEN the customer row is deleted
- THEN their orders are deleted

#### Scenario: Deleting an order with transactions is blocked

- GIVEN an order has an associated transaction
- WHEN the order is deleted
- THEN the delete is rejected by `ON DELETE RESTRICT`

### Requirement: Indexes

The system MUST define indexes on `orders.due_date` and `orders.status` to support agenda sorting and status filtering.

#### Scenario: Agenda indexes exist

- GIVEN the migrations are applied
- WHEN the schema indexes are inspected
- THEN indexes on `orders.due_date` and `orders.status` are present

### Requirement: Triggers

The system MUST provide a `set_updated_at()` trigger that refreshes `updated_at` on update for every table carrying the column.

> **DEFERRED (accepted, design-sanctioned)**: The `on_auth_user_created()` trigger that auto-creates a `profiles` row with `role = 'operator'` for each new auth user — and its backing `handle_new_user()` function — is intentionally deferred to the future auth change (design decision #4). No auth flow exists yet to verify against; profiles are seedable manually for local RLS tests until this lands. This deferral is recorded here so the source of truth does not claim an unbuilt trigger as delivered.

#### Scenario: Updated timestamp auto-refreshes

- GIVEN a row exists
- WHEN the row is updated
- THEN `updated_at` reflects the update time

#### Scenario: New auth user gets a profile

> **DEFERRED (accepted)** — `on_auth_user_created()` / `handle_new_user()` land in the future auth change; not implemented in this change.

- GIVEN a new auth user is created
- WHEN the trigger fires
- THEN a `profiles` row is created referencing the user with `role = 'operator'`
